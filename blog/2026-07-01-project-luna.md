# Project Luna 始動 — 自律する分身を、他社LLMに依存せず育てる設計

株式会社Cradleの第一号プロダクト **「Luna（ルナ）」** を始動した。
Lunaは、画面の中で寄り添う **2Dキャラクター（Live2D）** の姿を持ちながら、その裏側で
**AIエージェントが実務を自律的に代行する** —— 「コンパニオン × 自律型業務代行（AaaS）」の
ハイブリッドである。

本稿では、MVPを組むにあたって我々が最重要視した **2つの設計思想** を共有したい。
どちらも「目先の便利さ」ではなく「**会社として頭脳を自前で持つ**」という長期戦略から逆算した
ものだ。

---

## なぜ「顔」と「頭脳」を分けたのか

Lunaは大きく2つのアプリで構成される。

```
[ユーザー] ⇄ apps/web  (Next.js + Live2D「Luna」 + Chat UI)   ← 顔
                │  WebSocket（思考・発話・感情をリアルタイム配信）
                ▼
            apps/agent (FastAPI + 自律エージェント)            ← 頭脳
```

顔と頭脳は **WebSocketのメッセージ契約だけ** で疎結合に繋がる。顔は「Lunaがどう考えて
いるか」を知らなくていいし、頭脳は「Lunaがどう描画されるか」を知らなくていい。
両者は1ターンごとに次のようなイベントを交換する。

```
顔 → 頭脳 : user_message
頭脳 → 顔 : agent_thinking      （考え中…）
頭脳 → 顔 : tool_call           （ツール実行開始）
頭脳 → 顔 : tool_result         （実行結果）
頭脳 → 顔 : agent_token × N      （応答をストリーミング）
頭脳 → 顔 : agent_message        （最終応答 + emotion）
頭脳 → 顔 : done
```

最後の `agent_message` には `emotion`（neutral / happy / thinking / surprised / apologetic）が
乗る。顔はこれを受け取って **Lunaの表情** を切り替え、応答テキストが流れている間は
**口パク（リップシンク）** を有効にする。こうしてキャラクターの感情表現と、裏側の業務状態が
自然に同期する。

この分離のおかげで、「キャラの見た目」と「エージェントの賢さ」を **別々のチームが、別々の
速度で** 磨ける。これがプロダクトの拡張性を決定づけた。

---

## 設計思想 ①：LLM抽象化レイヤー —— 特定ベンダに依存しない

AIプロダクトの最大の経営リスクは、**頭脳を他社に握られること** だと我々は考えている。
価格改定もモデル廃止も、すべて他社の都合で起きる。

そこでLunaは、**最初からどのLLMにも依存しない** 構造で組んだ。頭脳の他の部分は、次の
抽象（インターフェース）だけを知っている。

```python
class LLMProvider(ABC):
    name: str
    model: str

    @abstractmethod
    def stream(self, messages: list[Message]) -> AsyncIterator[LLMChunk]:
        """応答をトークン断片でストリーム配信する。"""
        ...
```

この契約を満たす実装を差し替えるだけで、頭脳の供給元を切り替えられる。

```
LLM_PROVIDER=claude       # Anthropic Claude
LLM_PROVIDER=gemini       # Google Gemini
LLM_PROVIDER=self_hosted  # 自社/ローカルモデル（OpenAI互換）
LLM_PROVIDER=echo         # APIキー不要のローカルデモ
```

設定ファイルの **一行** を変えるだけ。アプリ本体のコードは一切変更しない。
キーやSDKが欠けていれば自動で `echo`（デモ用の頭脳）へ退避するため、開発環境は
**何があっても止まらない**。

注目すべきは `self_hosted` の存在だ。これはOpenAI互換のエンドポイント（自社推論サーバや
ローカルLLM）に繋ぐアダプタで、**将来Cradleが自社モデルを本番投入する日の接続口** に
なっている。その日、`LLM_PROVIDER` を `self_hosted` にするだけで、我々は他社LLMから
独立する。

## 設計思想 ②：データ・フライホイール —— 自社の頭脳を育てる燃料庫

「他社から独立する」と言うのは簡単だが、独立を支える燃料は **お金ではなくデータ** である。

そこでLunaは、**初日からすべての業務を教師データとして記録する** 設計にした。記録するのは
単なる会話ログではない。「**入力 → 思考 → 行動（ツール実行） → 結果**」という、業務の
構造そのものだ。

```python
@dataclass
class Trace:
    user_input: str          # 何を指示されたか
    thinking: list[str]      # どう考えたか
    tool_calls: list[...]    # 何を実行したか
    output: str              # どう応答したか
    emotion: str
    ok: bool
    provider: str
    model: str
    latency_ms: int
```

このトレースを JSONL（生ログ）と SQLite（集計・検索）の二系統に蓄積する。さらに、
そのまま微調整（Fine-tuning）に使える **SFT形式** へ書き出すメソッドを備えている。

```python
recorder.export_sft()   # {"messages": [...]} 形式のJSONLを生成
```

つまりLunaは、**Claude や Gemini を使って稼働しながら、その裏でこっそり「自社モデルを
育てるための教師データ」を溜め続ける**。使えば使うほど、独立への燃料が貯まる仕組みだ。

これが我々の言う「データ・フライホイール」である。

## 技術スタック

| レイヤー | 採用技術 |
|---|---|
| 顔（Frontend） | Next.js (App Router) / TypeScript / TailwindCSS / Framer Motion / Live2D |
| 頭脳（Backend） | Python / FastAPI / 自律思考ループ / WebSocket |
| LLM | 抽象化レイヤー越しに Claude / Gemini / 自社モデルを差し替え |
| 記憶・連携 | 短期メモリ（将来 PostgreSQL + pgvector）/ Redis |
| データ基盤 | SQLite + JSONL（教師データ）→ SFT書き出し |

なお「顔」については、本格的なLive2Dモデルを後から差し込めるローダを用意しつつ、MVP時点
では **追加依存ゼロで動く高品質なSVGアバター** を標準搭載した。金髪・色白の幼い少女Lunaが、
感情に応じて表情を変え、発話中は口パクし、待機中はまばたきと微かな揺れで「生きている感」を
出す。Live2Dモデルが配置されれば、自動でそちらへ切り替わる。

## 独立までのロードマップ

Lunaの開発は、最初から3段階の長期計画として設計されている。

| Phase | 頭脳 | データ |
|---|---|---|
| **① 借りる** | Claude / Gemini を抽象レイヤー越しに利用 | 全業務を教師データ化して蓄積開始 |
| **② 育てる** | 簡単な業務は蓄積データで微調整した自社モデル、難題のみ他社 | データ品質が向上 |
| **③ 独り立ち** | 自社モデルがほぼ全業務を担当 | 他社APIを切り離し独立 |

今はPhase①。だが、独立に必要な配管（抽象化レイヤー）と燃料庫（データ・フライホイール）は、
**初日からすべて敷設済み** である。あとは、Lunaが働けば働くほど、その日が近づく。

## おわりに

Lunaは単なる「喋るキャラAI」ではない。**自律して働く分身** であり、同時に **自社の頭脳を
育てるための装置** でもある。

「借り物の知能で稼ぎながら、自分たちの知能を育てる」——この二重戦略を、最初のコミットの
時点でアーキテクチャに刻み込めたことを、我々は誇りに思う。

次は、Lunaに本物の頭脳（LLM接続）と本物の業務ツール（検索・カレンダー・ファイル操作）を
与えていく。続報を待たれたい。
